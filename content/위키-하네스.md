이 위키의 기술 글은 사람이 직접 쓰지 않는다. **에이전트 하네스**가 쓰고, 검증하고, 발행한다. 이 노트는 그 파이프라인의 구조와 사용법을 기록한다. 하네스라는 개념 자체는 [[하네스-엔지니어링]], 이 위키의 전체 설계는 [[위키-설계-결정]] 참고.

## 구조 — 4개 에이전트, 6개 스킬

```
"~에 대해 글 써서 위키에 올려줘"
        │
[선행 리서치] (선택) 원문 정독 / deep-research → 00_*_facts.md
        │   ⚠️ 이 파일은 1차 소스가 아니다 — 파일 맨 위에 자기 경고를 박고,
        │      fact-checker가 원문으로 재검증한다. 리서치는 사실만 모으고
        │      엣지(인과·비교·일반화)는 만들지 않는다
[tech-writer] 도메인 캘리브레이션 → 00_domain_brief.md
        │ 공식·표준·대표 출처 2개 이상으로 통용 용어·피할 표기 확정
[tech-writer] 초안 작성 ─ tech-writing 스킬(작성 가이드)
        │ 01_writer_draft.md + (검증 필요) 마커
[fact-checker] ∥ [copy-editor]   ← 병렬, wiki-verify 스킬(검증 프로토콜)
 최신성·팩트·용어     오탈자·전문 문체 윤문
        │ FAIL이면 tech-writer 수정 루프 (최대 2회)
[병합 게이트] validate-note.py ─ frontmatter·마커 잔존·깨진 강조를 기계적으로 차단
        │ 통과 전 다음 단계 금지
[readability-reviewer] 최종 가독성 게이트 ─ readability-review 스킬
  잔존 AI 티·용어 접근성·자연스러움·전문 문체를 독자 눈으로 판정
        │ FAIL이면 용어→tech-writer 보강 / 문체→copy-editor 재윤문 (최대 2회)
[발행] wiki-note 방식 ─ temp clone → OKF v0.2 md → push → 자동 배포
```

| 구성요소 | 역할 |
|---|---|
| **tech-writer** (에이전트) | 본문 전 도메인·하위 분야와 표준 용어를 교정하고 `00_domain_brief.md`를 만든다. 정확하고 절제된 시니어 실무자 문체, 두괄식, 트레이드오프를 지킨다 |
| **fact-checker** (에이전트) | 최신성·팩트뿐 아니라 핵심 용어의 표기와 개념 경계를 공식 표준·문서·대표 논문에 대조한다. 비표준 직역·자의적 조어·개념 혼용은 팩트 오류다 |
| **copy-editor** (에이전트) | 오탈자·AI 티·홍보성 수사·가벼운 구어체를 다듬되, 정확한 표준 용어를 쉬운 말로 임의 치환하지 않는다 |
| **readability-reviewer** (에이전트) | 최종본의 AI 티·용어 접근성·자연스러움과 함께 과장·권위 호소 없는 전문 문체를 판정한다. 표준 전문용어는 난해하다는 이유만으로 문제 삼지 않는다 |
| **tech-writing** (스킬) | 글의 뼈대, 문장 규칙, OKF v0.2 + 위키 발행 프로필. `sources`·각주 출처 귀속, **연결의 근거**, 압축 위치 재확인, 집계 방법 병기 |
| **wiki-verify** (스킬) | 4종 검증(§최신성·§팩트·§오탈자·§윤문)의 기준과 PASS/FAIL 리포트 형식, 수정 루프 상한 |
| **readability-review** (스킬) | 최종 가독성 3축(§AI 티·§용어 접근성·§자연스러움) 판정 기준, 과검열 금지 원칙, 리포트 형식 |
| **wiki-post** (스킬) | 오케스트레이터 — 위 전부를 순서대로 엮고 실패를 처리한다 |
| **wiki-debug** (스킬) | 발행 뒤/실패 뒤 `_workspace` 산출물을 읽는 **사후 진단** — 게이트별 판정·FAIL 분류(수치/해석/기타)·⑦ 상류 전파 여부를 정리하고, ⑥ 회귀 계측 원장 행을 붙여넣기 직전까지 초안한다. 핵심은 원장 행을 쓰기 전 **현재 원격 원장을 재대조**(순번·창 상태·타 세션 추가)해 낡은 상태에 쓰는 사고를 막는 것. tinker-cookbook의 `/tinker:debug`에서 차용 |
| **validate-note.py** (게이트) | 발행 전 결정적 검증 — OKF v0.2 `type`, 위키 프로필 필드, `sources`↔각주, 신뢰·수명주기, Attested Computation 계약, 마커·렌더 결함을 기계 차단 |

모든 에이전트는 `model: inherit`으로 호출 런타임의 모델을 따른다. 서브에이전트가 없는 런타임에서는 역할을 순차 실행한다. `wiki-post`는 시작 전에 에이전트 4개·스킬 6개·검증기 존재를 확인하며, 필수 검증 실패를 SKIP하고 발행하지 않는다. `humanize-korean`만 선택 의존성이고, 없으면 copy-editor가 최소 윤문을 대체 절차로 실행한다. `.claude/` 실행본과 `claude-skill/` 배포본은 `claude-skill/check-sync.sh`로 동일성을 검사한다.

### OKF v0.2 적용 경계

- OKF 자체의 항상 필수 키는 `type` 하나다. 이 위키는 `title`·`description`·`tags`도 발행 게이트에서 요구한다.
- 새 출처는 `sources`에 두고 `sources[].id`와 본문 각주 라벨을 연결한다. `generated`와 `verified`를 분리하고, `status`·`stale_after`로 수명주기를 표시한다.
- 표준 Markdown 링크를 우선하되 기존 `[[위키링크]]`는 Quartz 확장으로 허용한다.
- `type: Attested Computation`은 `runtime`과 계산 계약을 추가 검증한다. `index.md`·`log.md`는 OKF 예약 파일이다.

## 설계 결정과 이유

- **작성과 검증의 분리.** 쓴 사람이 검증하면 자기 확증에 빠진다. fact-checker는 주장을 "확인"하지 않고 "반박"하려 시도하며, 반박에 실패한 주장만 통과시킨다.
- **전문성은 페르소나가 아니라 용어 계약으로 만든다.** "CTO처럼 써라"는 지시만으로는 그럴듯한 조어와 비표준 직역을 막지 못한다. 본문 전에 도메인·하위 분야를 특정하고, 권위 있는 출처 2개 이상으로 채택 표기·피할 표기를 기록한다. 작성자는 그 계약을 따르고 fact-checker가 개념 경계까지 재검증한다.
- **전문 문체는 난해함이 아니다.** 정확한 표준 용어와 조건·예외·트레이드오프는 보존하되, 과장·홍보 문구·가벼운 구어체·근거 없는 권위 호소는 제거한다. 쉬워 보이게 만들려고 전문용어를 부정확한 생활어로 바꾸는 것도 금지한다.
- **검증 2종은 병렬.** 팩트(내용)와 윤문(문체)은 서로 간섭하지 않으므로 동시에 돈다. 같은 문장을 둘 다 고치면 팩트 수정이 우선한다.
- **수정 루프에 상한(2회).** 무한 루프 방지. 2회 후에도 FAIL이면 발행을 중단하고 쟁점을 사람에게 넘긴다 — 강행은 사람의 승인이 필요하다.
- **발행은 재구현하지 않는다.** 기존 wiki-note 절차(temp clone→push→삭제, 로컬 무잔류)를 그대로 쓴다.
- **병합도 작업이므로 검증한다.** 에이전트 산출물을 사람이/오케스트레이터가 병합하는 단계가 유일한 무검증 구간이었다 — [[에이전트-평가-evals]]의 MAST '작업 검증 실패' 원칙을 적용해 결정적 게이트를 발행 앞에 세웠다.
- **읽기 경험은 기계 게이트가 못 본다.** validate-note.py는 마커·frontmatter 같은 *결함*을 막지만, 발행본을 처음부터 끝까지 독자 눈으로 읽는 사람은 파이프라인에 없었다. 병렬 윤문은 라인 단위라 통독 인상(문단 흐름, 잔존 AI 티, 대상 독자가 걸리는 용어)을 놓친다. 그래서 병합 뒤·발행 앞에 readability-reviewer를 최후 게이트로 세웠다 — 고치는 게 아니라 *판정*하고, FAIL이면 용어는 tech-writer·문체는 copy-editor로 되돌린다. 과검열(정착 용어를 취향으로 풀어쓰라는 지적)로 발행을 막는 것은 잔존 AI 티보다 나쁘므로, 애매한 지적은 참고로만 남긴다.
- **근거 파일도 검증 대상이다.** 오케스트레이터가 원문에서 뽑은 사실 파일(`00_*_facts.md`)이나 선행 리서치 산출물은 **1차 소스가 아니다.** 실제로 오케스트레이터의 추출 오류가 초안까지 전파된 적이 있고, 초안만 봐서는 잡히지 않았다 — 병합 단계가 그랬듯 이 구간도 무검증이었다. fact-checker가 원문으로 되짚는다.
- **경고를 단 근거 파일은 지켜지고, 안 단 파일은 전파된다.** ⑦은 *검증* 규칙이라 오류를 하류에서 잡을 뿐, 애초에 하류가 근거 파일을 어떻게 대하는지는 규정하지 않았다. AIDE² 편이 우연히 대조군이 됐다 — 오케스트레이터가 `⚠️ 1차 소스 아님, 전부 가설, 그대로 옮겨 쓰지 마라`를 맨 위에 박은 `00_critique_leads.md`는 작가가 그대로 지켰고, 같은 경고가 없던 `00_research.md`의 척도 비교는 작가가 **framing으로 물려받아** 초안까지 갔다(그게 그 편의 FAIL이다). 그래서 리서치 프롬프트에 둘을 넣는다: ⑴ **엣지를 만들지 마라** — 리서치는 사실을 모으고, 사실 사이의 인과·비교·일반화는 작가가 원문 근거로 만든다(특히 출처가 다른 수치끼리 비교 금지), ⑵ **산출 파일 맨 위에 자기 경고를 박아라.** 규칙을 사람의 기억에 맡기지 않고 파일 자신이 들고 다니게 하는 쪽이 싸다.
- **수치가 맞아도 해석은 틀릴 수 있다.** 검증에서 반증된 지적의 대부분은 틀린 수치가 아니라 **맞는 수치 위에 얹은 틀린 해석**(원문에 없는 인과·과잉 일반화)이었다. 그래서 §2 팩트 검증은 수치 전수 대조와 **별개로** 인과·비교·일반화를 반증한다.
- **노드는 검증되는데 엣지가 뚫린다 — 그래서 예방도 엣지에 건다.** 해석 FAIL이 세 편 연속 나고서야 공통 구조가 보였다. 사실 하나하나(노드)는 통과하는데(AIDE² 편은 수치 22건 전수 일치) **사실 둘을 잇는 순간**(엣지 — 인과 A→B, 일반화 A⊆B, 비교 A>B) 무너진다. tech-writing의 기존 규칙("모든 주장에 근거")이 안 문 이유가 여기 있다 — 양 끝 수치엔 근거가 있었고, 없던 건 *둘을 이어도 된다는 근거*였다. 규칙이 노드 수준에서 읽히고 실패는 엣지에서 났다. 검증 쪽엔 ⑧이 있는데 작성 쪽엔 대응물이 없어서, 같은 오류를 매번 새로 만들고 매번 잡았다(회당 약 126k, 사이클의 약 27%). 그래서 ⑧을 tech-writing에 미러링했다 — 탐지기를 더 붙이는 대신 이미 있는 규칙을 반대편에 복사하는 쪽. **근거는 실측이다**: AIDE² 편에서 오케스트레이터가 척도 비교를 콕 집어 경고한 곳은 초안이 지켰고(분리 각주까지 달았다), 경고하지 않은 곳에서 똑같이 넘어졌다. 능력이 아니라 커버리지 문제이니 일반 규칙이 통할 여지가 있다. **다만 과교정이 FAIL보다 나쁘다** — 해석은 이 위키의 값이고, 작가가 몸을 사려 전부 헤지하면 검증은 통과하고 글은 죽는다. 그래서 규칙은 "조심해라"가 아니라 "두 사실이 만나는 자리" 하나만 겨냥한다. 다음 2~3편에서 해석 FAIL이 줄지 않으면 규칙이 아니라 구조 문제다.
- **수치는 값이 아니라 방법과 함께 늙는다.** 발행 2주 뒤 전 위키 최신성 스윕을 돌리고 알았다. 논지는 거의 안 썩는데(사이트가 99 → 117개로 통째로 개편된 [[kinetics-뜯어보기]]조차 논지 8개가 전부 재현됐다) **직접 센 수치는 전부 썩는다.** 문제는 다시 세는 게 아니라 *같은 자로* 다시 세는 것이었다 — 집계 범위를 적어둔 수치는 재집계에 성공했고, 안 적은 수치는 세는 사람마다 값이 갈려(`ease` 82 vs 89 vs 101) 완화 표기로 물러나야 했다. 그래서 직접 센 수치엔 재현 명령·범위를 함께 남긴다. 1차 출처가 발표한 수치(논문 p값 등)는 해당 없다 — 거기선 출처 링크가 곧 방법이다.
- **하네스는 진화한다.** 실행에서 발견된 문제는 에이전트 정의에 반영하고 CLAUDE.md 변경 이력에 남긴다. 지금까지의 진화: ① copy-editor "대기 금지"(첫 실행에서 하위 작업 대기 중 정지), ② 병합 게이트·수치 전수 검사·UNVERIFIED 발행 규칙([[에이전트-평가-evals]] 원칙 자기적용), ③ 마크다운 렌더 검증·근사 표기 규칙(발행물에서 깨진 `**`·`~N` 발견), ④ 상류 근거 파일 검증·해석 검증(수치는 맞고 해석이 틀린 FAIL이 연속 발생), ⑤ 최종 가독성 게이트(readability-reviewer) 추가 — 윤문·병합을 통과하고도 발행본에 AI 티·난해 용어·비자연 문장이 남았고, 통독하는 검수자가 파이프라인에 없었다, ⑥ tech-writing에 '연결의 근거' 규칙 추가 — 해석 FAIL 3연속의 공통 구조가 '엣지'였고, 검증(⑧)에만 있던 대응물을 작성 쪽에 미러링했다, ⑦ 리서치 프롬프트에 엣지 금지·자기 경고 헤더 의무화 — 경고를 단 근거 파일은 지켜지고 안 단 파일은 framing째로 전파된다는 게 실측으로 드러남, ⑧ 직접 센 수치에 집계 방법 병기 — 전 위키 최신성 스윕에서 방법을 적어둔 수치만 재집계에 성공했다, ⑨ wiki-debug 스킬 추가(tinker-cookbook `/tinker:debug` 차용) — 발행 사후 진단·원장 행 초안을 얇게 코드화. 계기는 실측: tinker-cookbook 편에서 원장 행을 **낡은 상태에 대고 써** push 충돌 후 재작성했다(그새 다른 세션이 turbovec 편으로 ⑥을 확정했는데 확정 전 상태로 씀). 진단·형식화보다 "**행 쓰기 전 현재 원격 원장 재대조**"라는 절차가 핵심 방어.

**판정 기준** — 3편 중 해석 FAIL이 0~1편이면 ⑥ 유효, 2편 이상이면 규칙이 아니라 구조 문제다(규칙을 더 세게 쓰는 게 아니라 작성 단계의 구조를 다시 본다). 규칙이 생겼다고 FAIL을 관대하게 판정하면 측정이 오염되므로, fact-checker는 ⑥의 존재를 모른 채 평소대로 반증한다.

**창 상태(4편 참) — ⑥ 유효 쪽으로 기움, 다음 편에서 확정.** 네 편 중 해석 FAIL은 1편(서베이)뿐. 그간의 유보는 "나머지가 해석 FAIL *기회 자체가 없던* 편(수치 전수 일치·선제 차단)이라 ⑥이 막았다는 증거가 아니라 시험받지 않았다"는 것이었다. **그래프-엔지니어링 편이 그 공백을 메운다** — §95가 콕 집어 기다린 "엣지가 촘촘한 편"이었다(계승 서사·5↔3 매핑·순환 대립·척도 다른 수치). 여기서 ⑧이 *실제로 시험받고* 팩트 FAIL 0으로 버텼다: 초안이 매핑을 "이 글의 논증"으로 자기표시하고, 대립을 판정 않고 열어두고, 척도 비교를 본문에서 금지했다. 유일한 🟡(매핑 5:3 비대칭)도 FAIL이 아니라 완화 지적이었다. 다만 이 편은 **토론형**(3인 서브에이전트)이라 해석 리스크가 초안 전 토론에서 한 번 걸러진 구조 — "규칙 ⑥ 단독의 효과"와 "토론 구조의 효과"가 섞여 있어 순수 분리는 안 된다. 그래서 확정은 **비토론형 해석 고밀도 편(단일 tech-writer 논문리뷰류) 한 편**을 더 보고. 지금 판정: **⑥ 잠정 유효, 절 유지.**

**창 상태(5편 참) — 여전히 ⑥ 유효 쪽, 확정 조건 불변.** 다섯 편 중 해석 FAIL은 1편(서베이)뿐. cerebras-지식베이스 편이 다섯 번째인데 **또 토론형**(3인)이라, 방금 채운 공백을 다시 채우진 못한다 — 확정에 필요한 "비토론형 해석 고밀도 편"은 아직 안 왔다. 다만 이 편은 다른 방식으로 시험받았다: **1차 출처가 HTTP 500으로 닫혀** ⑦ 원문 직대조가 불가능한 상황에서, fact-checker가 상류 근거 파일+외부 교차검증으로 물러서고 UNVERIFIED를 정직하게 남겼다 — 검증이 "원문을 못 보면 통과시킨다"로 무너지지 않았다는 기록. 해석 측면에선 smoothing 60·조직경계 전제 등 엣지가 있었으나 초안이 귀속·마커로 처리해 팩트 FAIL 0. 지금 판정: **⑥ 잠정 유효, 절 유지. 비토론형 편 한 편 더 대기.**

**창 상태(6편 참) — ⑥ 확정: 유효. 대기하던 조건이 채워졌다.** 여섯 편 중 해석 FAIL은 여전히 1편(서베이)뿐 — 판정 기준(3편 중 0~1편이면 유효)을 6편 창에서도 만족. 그리고 §99·§101이 확정을 걸어둔 조건, **"비토론형·해석 고밀도 단일 tech-writer 편"이 turbovec-벡터압축으로 도착했다.** 이 편은 토론 필터가 없어 ⑧/⑥이 초안에서 홀로 시험받았고, 시험 자체가 진짜였다 — 이번 편엔 앞선 어느 편에도 없던 **개체 혼동**(Google=알고리즘 vs 커뮤니티=라이브러리를 2차 블로그가 한 문장에 합침)이라는 새 함정까지 있었는데, 초안이 그걸 잡아 글의 뼈대로 삼고, 척도 다른 FAISS 비교를 조건별로 분해하고, "학습 없음→우위" 인과를 근거 있는 데까지만 좁혔다. 팩트 FAIL 0. 이로써 ⑥은 "그럴듯한 해석을 작성 단계에서 좁히는 규칙"으로 **가설을 벗고 확정**된다. 남는 주의 하나: 표본 6편 중 해석 FAIL이 난 1편은 규칙 도입 *직전* 편(서베이)이고, 도입 이후 5편은 전부 FAIL 0 — 즉 규칙이 실패를 *줄였다*기보다 실패가 애초에 안 나는 편들이 이어졌을 가능성을 완전히 배제하진 못한다. 그래도 turbovec 편은 "실패할 함정이 실재했는데 안 났다"를 보였으므로, 능력이 아니라 규칙의 커버리지 효과라는 애초 가설([[에이전트-평가-evals]] §노드-엣지)에 부합한다. **판정: ⑥ 확정(유효). 이 측정 절은 소임을 다했다 — 이후 편은 FAIL 분류를 계속 원장에 남기되, "측정 중" 프레임은 종료한다.** wiki-post 스킬의 ⑥ 측정 지시·CLAUDE.md 이력·README를 같은 사이클에서 동기화.

**회귀 계측(7편 참) — tinker-cookbook, 회귀 없음.** 확정 뒤 첫 편도 비토론형 단일 tech-writer였고 엣지가 여럿(θ/Σ 서베이 연결·"저수준 중간층" 인과·벤더 스킬 일반화)이었다. 다 버텼다 — 초안이 인과는 `(추정)`으로 자기표시하고, θ/Σ는 `(검증 필요)` 마커를 달았다가 병합 때 서베이 원문(θ쪽 "거의 닫혀 있다")을 직대조해 근거 있는 엣지로 승격시켰다. 팩트 FAIL은 해석이 아니라 **기타(출처 귀속)** 1건뿐 — "README/공지 모두"를 "공지만"으로 좁힌 것. 해석 FAIL 0 유지. ⑥ 확정 판정에 회귀 신호 없음.

**회귀 계측(8편 참) — ai-native-ai-dlc-토론, 회귀 없음.** 4번째 토론형(3직군×2R). 이 편은 **⑦(상류 근거 검증)이 다시 설계대로 작동한 사례**다 — 리서치 `00_research.md`가 "AWS 원문에 Amazon Q 언급 없다"고 단정했는데 fact-checker가 원문에서 Q(저자 약력 "Amazon Q Developer 챔피언")를 찾아 반박, 하중 주장(도구=Claude Code)만 남기고 "언급 없다"를 걷어냈다. 해석 측면에선 토론 구조가 리스크를 초안 전에 흡수 — 세 소스의 축(실험서사/생명주기/성숙도)을 포개지 말라·병목 수렴은 "화자에게 불리한 자백이라 증거력↑"이되 "세 성공 사례라 생존자 편향"이라는 이중 라벨·"2주"→≈5주 분리가 전부 R1/R2 트랜스크립트에서 나와 초안에 선제 반영됐다. 팩트 FAIL은 해석·수치 0, 🟡 4건 전부 인용 충실도/귀속(기타). ⑥ 확정에 회귀 없음. 토론형 4편·비토론형 3편(핸드북·서베이 제외 뒤 tinker) 모두 해석 FAIL 0 유지 — 단 토론형은 리스크가 토론서 한 번 걸러지는 구조라 여전히 "순수 ⑥ 효과"와는 섞인다.

**회귀 계측(10편 참) — claude5-컨텍스트-엔지니어링-새-규칙, 확정 후 첫 해석 FAIL.** (9편째 boris-cherny는 표에만 행이 있고 이 문단이 비어 있었다 — 판정은 "기타 2건·해석 0·회귀 없음"으로 그 행에 적혀 있다.) 이번 편은 비토론형 단일 tech-writer였고, ⑥ 확정 이후 세 편(tinker·ai-native·boris)이 전부 `기타`였던 흐름이 여기서 끊긴다. **다만 어떻게 났는지가 판정보다 중요하다** — 초안은 §실무 적용에서 삭제 순서를 "내일 할 수 있는 순서로 적는다"며 **자기 것으로 정확히 표시해놓고**, §결론부터의 요약 한 줄에서 같은 순서를 "원문이 제시하는"으로 되돌려 붙였다. 즉 규칙이 안 지켜진 게 아니라 **지켜진 뒤 요약 위치에서 샜다.** 이 편의 나머지 엣지는 훨씬 위험했는데 다 버텼다: 진단의 범위(시스템 프롬프트·CLAUDE.md·스킬)와 측정의 범위(시스템 프롬프트만)를 갈라 "CLAUDE.md를 80% 줄여도 된다"는 확장을 차단했고, "예시를 주지 마라"를 도구 사용법 한정으로 못 박아 few-shot 일반으로 번지지 않게 했으며, 비율(80%)에서 절대 효과를 추정하지 않았고, 세션 관찰 3건을 n=1로 못 박아 원문 주장의 입증으로 쓰지 않았다. **가설**: 엣지 위험은 본문보다 **요약·리드·표 같은 압축 위치**에 몰릴 수 있다 — 압축이 곧 연결을 만드는 작업이기 때문. 근거는 아직 이 한 편뿐이라 규칙화하지 않는다. **판정: ⑥ 유효 유지, 재고 아님**(재고 조건은 2편 연속). 다음 편에서 또 해석 FAIL이 나면, 특히 또 압축 위치에서 나면, 규칙을 세게 쓰지 말고 작성 단계 구조를 다시 본다.

**회귀 계측(11편 참) — ai-prd-리뷰어-토론, 해석 FAIL 2편 연속. 재고 조건 발동.** 바로 앞 문단이 걸어둔 조건("다음 편에서 또 해석 FAIL이 나면, 특히 또 압축 위치에서")이 **다음 편에서 곧바로 충족됐다.** 그것도 예고된 형태 그대로다 — claude5 편은 §결론부터의 요약 한 줄에서, 이 편은 §이전 가능한 것(결론·처방 절)에서 샜고, 두 편 다 **본문 앞부분에서 "원문에 없다"를 정확히 표시해놓고 뒤쪽 압축 위치에서 그 빈칸을 단정으로 채웠다.** 압축이 곧 연결을 만드는 작업이라는 가설이 n=1에서 n=2가 됐다. 규칙 자체가 안 지켜진 게 아니라는 점도 두 편이 같다: 이 편의 나머지 엣지는 오히려 까다로웠는데 다 버텼다(여섯 관점이 원문에 제기한 주장 중 둘을 원문 대조로 되꺾었고, 척도 다른 수치 비교는 본문에서 금지를 명시했다).

**다만 이 편은 앞 편과 결정적으로 다른 변수를 하나 더 갖고 있어 "압축 위치" 가설과 섞인다.** FAIL의 뿌리가 초안의 압축 실수가 아니라 **상류 토론 파일**이었다 — `00_debate_1_backend.md`가 문제의 두 주장에 `[의견]`·`[확인 불가]` 라벨을 정확히 달아뒀는데 초안이 **라벨만 떨어뜨리고 내용을 가져왔다.** 파일 상단 자기 경고 헤더는 6개 토론 파일 전부에 붙어 있었고(검사 6/6) 규칙 ⑦도 설계대로 작동해 fact-checker가 뿌리를 특정했다. 즉 실패한 건 헤더도 ⑦도 아니고, **헤더가 "이 파일은 1차 소스가 아니다"까지만 말하고 문장 단위 라벨의 보존 의무는 규정하지 않는다**는 공백이다. 07-17에 "파일이 경고를 들고 다니게 한다"로 푼 문제의 한 층 아래가 드러난 셈이다.

**판정: ⑥은 여전히 유효로 두되(규칙이 겨냥한 엣지 대부분은 두 편 모두에서 버텼다), 재고 조건이 발동했으므로 규칙을 세게 쓰지 않는다.** 07-17 이력이 스스로 못 박은 대로 "탐지기 추가 대신 구조를 본다". 다음 사이클에서 사용자와 논의할 후보 둘: ⑴ **압축 위치 검증** — 요약·리드·결론·표처럼 압축이 일어나는 자리를 본문과 다른 강도로 훑는 절차(두 편 연속 같은 자리에서 샜다). ⑵ **라벨 보존 규칙** — 상류 산출물의 `[의견]`/`[확인 불가]` 같은 문장 단위 표시를 하류가 떨어뜨리지 못하게 하는 규정(헤더만으로는 안 걸린다는 게 이번 실측). 둘 중 어느 것도 아직 규칙으로 쓰지 않는다 — 근거가 각각 2편·1편이고, 과교정이 FAIL보다 나쁘다는 07-17 판단은 그대로다.

**회귀 계측(14편 참) — dogwood-런타임-검증, 해석 FAIL은 계속되나 유형이 뒤집혔다.** (12·13편째 에이전트-팀·심리테스트는 표에만 행이 있고 이 문단이 비어 있다 — 판정은 각 행에 적혀 있다.) 비토론형 단일 tech-writer이고 1차 소스는 벤더 블로그 전문이다. 정책 코드와 이벤트 트레이스 14블록이 바이트 단위로 전수 일치해 **수치 FAIL 0**이었고, 팩트 FAIL은 해석 2·기타 2로 났다.

**앞 네 편과 방향이 반대라는 점이 이번 판정의 핵심이다.** claude5·ai-prd·에이전트-팀·심리테스트의 해석 FAIL은 모두 **압축 위치에서 빈칸을 단정으로 채우는** 확장형이었다. 이번 편의 주 FAIL은 그 반대다 — 초안이 원문의 "감사와 집행이 기대는 보장이 그대로 이어진다"를 직전 문장(판정 해소 규칙)만 가리킨다고 **좁혀서** 읽었고, 그 좁힘이 틀렸다. 정관사+복수 명사구가 앞에서 정의된 보장(결정성)을 되불러오며 그 명사구가 정의된 자리는 원문에 한 곳뿐이다. 게다가 설계상으로도 결정성은 사라지지 않았다. **헤지가 곧 안전은 아니라는 기록이다** — 근거 없는 확장만이 아니라 근거 없는 축소도 원문 왜곡이 된다. ⑥은 "연결의 근거를 대라"고 하지 "연결을 끊을 때도 근거를 대라"고는 하지 않는다.

**압축 위치 패턴 자체는 재현됐다. 다만 FAIL이 아니라 🟡로 잡혔다.** 재검증에서 새로 나온 유일한 해석 지적이 "바뀐 것은 보장이 아니라 감사와 재현의 단위다"라는 **문단 머리 요약 한 줄**이었고, 바로 앞 문단이 "보장이 성립하는 단위가 바뀌었다"고 말해놓고 이 줄에서 "보장은 안 바뀌었다"로 뒤집혔다. §123·§124·§125가 지목한 바로 그 자리에서 또 났다는 점에서 가설은 유지되지만, 이번에는 FAIL로 굳기 전에 걸렸다.

**⑦은 설계대로 작동했고, 이번에는 작성 쪽에서 작동했다.** `00_research.md`의 2차 출처 관찰 4건(InfoQ의 "참조 구현은 프로덕션용이 아니다", GitHub CONTRIBUTING 모순설, MCP 명세, 저장소 구조)은 전부 미검증 라벨을 달고 격리돼 있었고 **초안이 하나도 쓰지 않았다.** 그중 InfoQ 건은 재검증 회차에 저장소 README 원문으로 확인돼 확정 사실로 승격됐다(turbovec·boris·claude5·에이전트-팀에 이은 **유보 → 승격 다섯 번째**). CONTRIBUTING "모순"도 읽기 전용 미러라는 사실로 해소됐다. 상류 전파로 인한 FAIL은 0이다.

**최신성 FAIL 1건은 이 파이프라인에서 드문 유형이다.** 초안이 "원문에 답이 없다"고 **정확히** 적은 질문을, 작성일 9일 전 AWS가 다른 글에서 이미 답했다. 1차 출처 대조만으로는 안 잡히고 **후속 발표를 찾아야** 잡히는 종류다. 수정은 논지를 되레 강화했다 — "원문에 답이 없다"에서 "경계는 언어가 정하지 않고 실행 환경이 정하며, 관리형과 자체 호스팅의 기본값이 서로 반대다"로.

**후기(같은 날) — 규칙 ⑨가 이 편의 발행본에서 결함 하나를 더 찾았다.** 압축 위치 검증을 `wiki-verify §2`에 ⑨로 넣고, 문안이 실제로 작동하는지 이 편의 **초안**에 단독 적용해봤다(다른 리포트는 열지 못하게 격리). 압축 위치 31개를 훑어 🔴 1건이 나왔고, 그것이 **발행본까지 살아 있었다** — 원문 `That's **part of** the reason why we decided to develop a new language`에서 한정어 `part of`가 탈락해 "그것이 새 언어를 만든 이유다"로, 즉 **유일한 이유**가 되어 있었다. 하필 §6의 마무리 볼드 문장이고 바로 뒤 문장이 그 전제 위에 서서 한 칸 더 증폭됐다. 팩트체크·재검증·가독성 세 게이트가 모두 놓친 자리다 — 앞뒤 두 문장이 원문에 충실해서 **본문 패스로는 한정어 하나의 탈락이 묻힌다.** ⑨의 "별도 패스" 요구가 정확히 이걸 잡았다. 발행본은 🔴 1건과 🟡 3건(서두의 "이 셋"과 §6 표의 셋이 내용이 다른데 같은 이름으로 불림 / §1의 근거 없는 분포 주장 "대부분" / §9의 원문에 없는 단정 "감사할 수 없고")을 정정해 재발행했다.

**이 시험이 ⑨ 문안의 구멍도 드러냈다.** ⑨는 "압축한 **본문 자리**를 찾고"라고만 쓰는데, 이번 🔴은 같은 글의 본문만 봐서는 안 잡히고 **1차 소스와 대조해야만** 잡힌다. 이번에 잡힌 건 과제 지시문이 "원문이 기준"이라고 따로 못 박아준 덕이었고, 이는 2026-07-12 이력의 *"잡힌 건 규칙이 아니라 프롬프트에 우연히 적어준 덕"* 과 같은 구조다. 그래서 ⑨에 둘을 보강한다 — ⑴ 대조 기준은 **같은 글의 본문과 1차 소스 둘 다**이며 **원문이 스스로 단 한정어**(`part of`·`currently`·`might`·`we expect`)의 탈락이 대표 유형이다, ⑵ 기준 ②(축 압착)에 확정선을 준다 — **같은 글 안에 서로 다른 내용의 같은 이름 목록이 두 벌 생겼는가**. 기준 ①은 "사라진 어절"이라는 물증이 있어 판정이 안 흔들렸고 지적 7건 중 5건이 ①에서 나왔다.

**판정: ⑥ 유효 유지.** 재고 조건은 §123에서 이미 발동했고 그 결론(규칙을 세게 쓰지 말고 작성 단계 구조를 사용자와 논의)은 그대로다. 이 편이 논의에 보태는 후보가 하나 있다. ⑶ **축소도 연결이다** — 원문 주장의 범위를 좁히는 서술에도 확장과 같은 강도의 근거를 요구할지. 근거가 아직 1편뿐이라 규칙으로 쓰지 않는다.
