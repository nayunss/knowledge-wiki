프롬프트를 길게 다듬지 않으면 결과도 거칠어질까. 이번에는 요구사항을 평범한 한국어로 전달하고, 별도의 프롬프트 최적화 과정 없이 작은 사주 웹앱을 만들었다. 실행 환경은 사용자가 지정한 Codex `gpt-5.6-sol`, `default fast`였다.

결론부터 말하면 **작고 경계가 분명한 제품에서는 프롬프트 최적화보다 범위 제한, 기존 작업 지침, 환경 검증이 완성도에 더 직접적으로 작용했다.** 다만 이 결론은 코드 작성 과정에만 해당한다. AI가 만든 사주 해석의 품질은 실제 사용자 평가나 정답 데이터로 검증하지 않았다.

## 무엇을 만들었나

출발점은 `.git` 디렉터리만 있는 빈 저장소였다. 요구사항은 네 가지였다.

1. 사용자가 생년월일시를 입력한다.
2. Upstage와 Gemini 중 하나를 고른다.
3. 사용자가 자신의 API 키를 직접 입력한다.
4. 선택한 AI가 사주 해석을 반환한다.

최종 산출물은 `index.html`, `styles.css`, `app.js`, `README.md` 네 파일이다. 빌드 도구나 패키지 설치 없이 `python3 -m http.server 4173`으로 실행되는 정적 웹 앱을 택했다. 빈 저장소에서 기능을 확인하기까지 필요한 변수를 줄이기 위한 선택이었다.

화면에는 양력·음력, 생년월일, 출생 시간, 시간 모름, AI 제공자, API 키 입력을 배치했다. 결과 영역은 빈 상태, 로딩, 성공, 오류 상태를 나눴다. 작은 앱이지만 성공 화면 하나만 만드는 대신 요청의 전체 생명주기를 구현했다.

## 프롬프트 최적화 없이 무엇이 입력을 대신했나

프롬프트 최적화 스킬은 쓰지 않았지만, 아무 맥락 없이 모델에 맡긴 것은 아니다. 저장소 작업 규칙, 디자인 스킬의 체크리스트, 도구 사용 제약이 이미 실행 환경을 감싸고 있었다. [[하네스-엔지니어링]] 관점에서 보면 사용자 프롬프트를 길게 만드는 대신 하네스가 작업 방법을 제한했다.

특히 디자인 지침은 접근성, 반응형, 로딩·오류 상태, 다크 모드, 모션 감소 설정을 빠뜨리지 않게 했다. 사용자 문장에는 이 항목들이 없었지만, 구현 체크리스트에는 있었다. 이번 작업에서 “프롬프트를 최적화하지 않았다”는 말은 “명세가 없었다”는 뜻이 아니다. 명세의 일부가 프롬프트 밖에 있었다.

또 하나는 요구사항의 닫힌 범위다. 페이지가 하나이고, 데이터베이스도 인증도 배포도 없었다. 입력, 제공자 선택, API 호출, 결과 표시라는 흐름이 짧았다. 이런 문제는 모델이 추측해야 할 제품 정책이 적다. fast 설정이 잘 맞았다고 느낀 이유도 모델의 절대 성능을 측정해서가 아니라, 작업의 불확실성이 낮았기 때문이다.

## 구현에서 잘된 선택

### 의존성을 늘리지 않았다

빈 저장소에서 React나 Next.js를 먼저 올리지 않고 HTML, CSS, JavaScript로 끝냈다. 이 앱의 상태는 폼과 API 요청 정도다. 프레임워크를 추가하면 얻는 것보다 설치, 빌드, 번들 검증이 늘어날 가능성이 컸다.

이 선택 덕분에 JavaScript 문법 검사와 정적 서버 응답만으로 기본 동작을 빠르게 확인할 수 있었다. 나중에 라우팅, 계정, 저장된 상담 기록이 필요해지면 그때 애플리케이션 프레임워크로 옮기는 편이 낫다.

### API 키의 저장 범위를 줄였다

키 입력은 비밀번호 필드와 `autocomplete="off"`로 만들었다. 코드에는 `localStorage`, `sessionStorage`, 쿠키 저장이 없다. 키는 요청을 보내는 동안 브라우저 메모리에만 머문다.

이 방식은 운영자가 사용자의 키를 보관하지 않는다는 장점이 있다. 그러나 “안전하다”와 같은 뜻은 아니다. 브라우저가 선택한 제공자에게 직접 요청하므로 키는 클라이언트 코드가 접근할 수 있고, XSS가 생기면 노출될 수 있다. 공개 서비스라면 CSP(Content Security Policy), 공급자별 키 제한, 서버 프록시 여부를 다시 설계해야 한다.

### 사주 계산을 아는 척하지 않았다

이 앱에는 만세력 계산 엔진이 없다. 생년월일시만으로 정확한 사주 원국을 계산하려면 달력 변환, 절기, 지역과 시간 보정 같은 규칙이 필요하다. LLM이 이 계산을 대신한 척하면 그럴듯한 오류가 나온다.

그래서 시스템 입력에 “천간지지나 일주를 확실히 계산할 수 없다면 지어내지 말라”는 제한을 넣었다. 이 방어는 오답을 정답으로 바꾸지 않는다. 다만 계산 근거가 없는 모델이 단정하는 실패를 줄이는 최소 장치다.

### 모델 변경이 한곳에 모여 있었다

처음에는 Upstage `solar-pro3`, Gemini `gemini-3.7-flash`를 연결했다. 이후 요청에 따라 각각 `solar-pro2`, `gemini-3.6-flash`로 낮췄다. 화면의 모델 표기와 API 요청의 모델 ID만 함께 바꾸면 됐다.

이 변경이 작았던 이유는 제공자별 호출을 `callUpstage`, `callGemini`로 분리했기 때문이다. 모델 선택이 여러 이벤트 핸들러에 흩어졌다면 간단한 비용 조정도 회귀 위험을 키웠을 것이다.

## fast에서 빨랐던 것과 사람이 확인해야 했던 것

코드 생성은 빨랐다. 폼 구조, 반응형 CSS, 제공자별 fetch, 상태 전환이 한 번에 만들어졌다. 작은 UI의 반복적인 배선에는 fast 설정이 충분했다는 것이 이번 한 건의 관찰이다.

반대로 외부 API 모델명은 기억에 맡길 수 없었다. Upstage와 Gemini 모델은 바뀔 수 있으므로 공식 페이지를 확인했다. 코드가 빠르게 나오는 것과 현재 API를 정확히 아는 것은 다른 문제였다. 특히 모델 ID 같은 시간 민감 정보는 생성 속도와 무관하게 조회가 필요하다.

검증에서도 경계가 드러났다. `node --check`, `git diff --check`, HTML 파싱, 로컬 HTTP 응답은 통과했다. 하드코딩된 키와 브라우저 저장소 사용도 검색으로 확인했다. 그러나 자동화 브라우저 CLI가 없어 스크린샷 검증을 하지 못했고, 실제 유효 키로 AI 응답을 받는 종단 간 테스트도 하지 않았다. “실행된다”는 말의 범위는 여기까지다.

## 트레이드오프와 맞지 않는 경우

이 접근은 프로토타입에 맞는다. 한 화면, 개인 API 키, 저장하지 않는 결과, 낮은 운영 복잡도가 조건이다. 다음 요구가 붙으면 그대로 확장하기 어렵다.

- 정확한 사주 원국과 대운 계산이 필요하면 검증된 만세력 라이브러리나 서버 계산기가 필요하다.
- 상담 기록을 저장하려면 인증, 데이터베이스, 개인정보 보존 정책이 필요하다.
- 운영자가 API 비용을 부담하려면 키를 브라우저에 노출하지 않는 서버 API가 필요하다.
- 제공자가 브라우저 CORS 요청을 제한하면 프록시 계층이 필요하다.
- 해석 품질을 제품 가치로 삼으려면 프롬프트 버전 관리와 평가 데이터셋이 필요하다.

마지막 항목이 중요하다. 이번에는 프롬프트 최적화를 쓰지 않아도 웹앱의 껍데기를 만들 수 있었다. 하지만 사주 해석의 일관성, 유해 표현, 시간 미상 처리, 음력 입력 해석을 비교하려면 프롬프트와 평가를 함께 다뤄야 한다. 구현 속도가 콘텐츠 품질 검증을 대신하지 않는다.

## 다음에는 무엇을 바꿀까

첫째, 생년월일시를 바로 LLM에 보내지 않고 만세력 계산 결과를 구조화된 JSON으로 만든다. LLM은 계산기가 아니라 설명기로 제한한다.

둘째, 제공자 어댑터를 별도 모듈로 분리하고 모델 ID를 설정 객체로 모은다. 지금은 두 제공자뿐이라 함수 두 개로 충분하지만, 모델 교체가 반복되면 설정과 UI 표기가 어긋날 수 있다.

셋째, 최소 평가 세트를 만든다. 시간 있음·없음, 양력·음력, 잘못된 키, 빈 응답, 제공자 오류를 고정 사례로 두고 UI 상태와 해석 안전성을 각각 검사한다. 이는 [[에이전트-평가-evals]]에서 말하는 생성과 검증의 분리와 같은 문제다.

## 이번 작업에서 남은 결론

프롬프트 최적화를 하지 않았는데도 결과가 나온 이유를 모델 성능 하나로 설명하면 중요한 부분을 놓친다. 작은 범위, 이미 존재한 작업 규칙, 공식 문서 조회, 실행 환경의 피드백이 함께 작동했다.

Codex `gpt-5.6-sol`, `default fast`는 이번 세션에서 사용자가 지정한 환경이다. 이 한 건으로 다른 모델이나 설정보다 낫다고 말할 근거는 없다. 다만 요구사항이 닫혀 있고 검증 명령이 분명한 작은 프론트엔드 작업에서는, 긴 프롬프트보다 빠른 구현과 즉시 검증의 반복이 실용적이었다.
