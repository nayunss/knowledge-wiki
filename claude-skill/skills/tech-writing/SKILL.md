# tech-writing — 기술 글 작성 가이드

knowledge-wiki에 올라가는 모든 기술 글의 작성 표준. "누가"는 tech-writer 에이전트, "어떻게"가 이 문서다.

## 0. 도메인 캘리브레이션 (본문보다 먼저)

글을 쓰기 전에 `_workspace/00_domain_brief.md`를 만든다. 길게 조사 보고서를 쓰는 단계가 아니라, **이 분야 사람이 어떤 개념과 말을 쓰는지 맞추는 단계**다.

1. 주제의 도메인과 하위 분야를 한 줄로 특정한다. 같은 단어가 분야마다 다른 뜻이면 이번 글의 의미 범위를 적는다.
2. 용어 기준 출처를 최소 2개 확인한다. 우선순위는 공식 표준·공식 문서·대표 논문·전문 학회/재단·널리 쓰이는 실무 문서 순이다. 개인 블로그만으로 표준 용어를 확정하지 않는다.
3. 핵심 용어 표를 만든다: `개념 | 채택 표기 | 첫 등장 표기 | 피할 표기 | 근거 URL`.
4. 한글과 영문 중 현업에서 실제로 통용되는 쪽을 기본 표기로 택한다. 억지 번역보다 원어가 정확하면 원어를 쓰고 첫 등장에만 설명한다.
5. 표준이 갈리는 용어는 하나를 조용히 정답처럼 만들지 않는다. 주요 대안과 선택 이유를 짧게 남긴다.

`00_domain_brief.md`는 방향을 잡는 상류 산출물이지 1차 출처가 아니다. fact-checker가 원문에 다시 대조한다.

```markdown
# 도메인 브리프
- **도메인**: ...
- **하위 분야**: ...
- **대상 독자**: ...

## 용어 기준 출처
- https://...  # 최소 2개
- https://...

## 핵심 용어
| 개념 | 채택 표기 | 첫 등장 표기 | 피할 표기 | 근거 |
|---|---|---|---|---|
| ... | ... | ... | ... | URL 또는 출처 id |
```

## 1. 글의 뼈대 (순서대로)

1. **후킹 도입 (2~4문장)** — 독자가 겪는 문제 또는 뒤집히는 통념으로 시작한다. "X란 무엇인가" 사전식 도입 금지.
2. **핵심 주장 선언 (두괄식)** — 이 글이 말하려는 것 한 문단. 독자가 여기까지만 읽어도 결론을 안다.
3. **본문** — 주장을 지탱하는 섹션들. 각 섹션도 두괄식. 비교는 표, 절차는 번호 목록, 구조는 코드블록/다이어그램.
4. **트레이드오프 섹션 (필수)** — 한계, 안 맞는 경우, 대안. 이 섹션이 없으면 미완성 글이다.
5. **실무 적용 (권장)** — "그래서 내일 뭘 하면 되나". CTO 시각: 도입 판단 기준, 비용, 팀 역량 요구.
6. **관련/출처** — 관련 개념은 위키링크로 연결하고, 외부 근거는 frontmatter `sources`와 본문 각주로 주장 단위 귀속한다.

## 2. 문장 규칙

- 한 문단 = 한 생각. 5문장 넘으면 쪼갠다.
- 문장 길이에 리듬을 준다 — 긴 문장 뒤엔 짧은 문장.
- 수식어보다 구체 수치·사례. "매우 빠르다" 대신 "p99 12ms".
- **네가 직접 센 수치엔 집계 방법을 함께 남겨라.** 개수·바이트·빈도처럼 손으로 잰 값은 재현 명령이나 집계 범위를 본문 표나 `## 출처`에 적는다 — 예: ``grep -o 'data-lang="css"' index.html | wc -l`` → 198. 몇 주 뒤 그 수치가 낡았을 때, 방법이 있으면 같은 자로 다시 재고 없으면 못 잰다. **실측**: kinetics 편은 집계 범위("이펙트 CSS 세 파일의 transition·animation 선언 내")를 적어둔 덕에 사이트가 99 → 117개로 개편된 뒤에도 전 수치를 재집계할 수 있었다. 같은 글에서 방법을 안 적은 수치는 세는 사람마다 값이 갈려(`ease` 82 vs 89 vs 101) 재현에 실패했다.
  - 1차 출처가 발표한 수치(논문의 p값, 벤더의 벤치마크)엔 해당 없다 — 그건 출처 링크가 곧 방법이다. **네가 센 것에만** 붙인다.
- 용어 첫 등장 시 `00_domain_brief.md`에서 정한 통용 표기를 쓰고 필요하면 한글(영문)을 병기한 뒤 한 줄로 설명한다. 이후 표기를 통일하고 반복 설명하지 않는다.
- 능동태 기본. 번역투("~에 의해", "~되어진다") 금지.
- 문체는 해당 분야의 시니어 실무자가 동료에게 기술 검토를 설명하는 수준으로 맞춘다. 정확하고 절제되며, 조건과 예외를 분명히 쓴다.
- 홍보 문구("혁신적", "게임 체인저"), 근거 없는 최상급, 감탄, 과도한 독자 호명, 가벼운 대화체, 권위적인 단정은 쓰지 않는다.
- 전문적으로 보이기 위해 명사·영어·약어를 쌓지 않는다. 전문성은 용어 난도가 아니라 개념 경계·전제·트레이드오프의 정확성에서 나온다.

## 3. 설득의 구조

- **주장 → 근거 → 예시** 3박자. 근거 없는 주장은 쓰지 않거나 "추정"으로 명시.
- **두 사실을 잇는 문장은 그 연결의 근거를 대라.** 수치가 각각 맞아도 사이의 **인과·비교·일반화**는 별개 주장이다. 원문이 "A라서 B"라고 했나, 아니면 A와 B를 따로 말했나? 좁은 사실 하나에서 넓은 결론으로 건너뛰지 않았나? 특히 **척도가 다른 수치는 비교하지 마라** — 다른 벤치마크·다른 통계 처리는 변환 정의가 없으면 대소 자체가 성립하지 않는다. 연결의 근거를 원문 문장으로 못 대면 쓰지 말거나 `(검증 필요)`.
  - 이건 몸을 사리라는 말이 **아니다.** 해석은 이 위키의 값이다 — 날 선 주장을 쓰되, 그 주장이 딛는 연결이 원문에 있는지만 확인하라. 겨냥 지점은 "두 사실이 만나는 자리" 하나다.
  - **압축 위치를 특히 조심하라.** 요약·리드·결론·표는 본문을 눌러 담는 자리이고, 눌러 담는 행위가 곧 연결을 만든다. 본문에서 단 유보·귀속 라벨을 요약에서 떨어뜨리지 마라. 원문이 스스로 단 한정어(`part of`·`currently`·`might`)도 마찬가지다.
- **마커를 달기 전에 1차 출처를 한 번은 열어봐라.** `(검증 필요)`·UNVERIFIED는 확인을 포기하는 자리가 아니라 확인에 **실패한** 자리다. 1차에서 확인되면 마커 없이 근거를 달고, 못 닫히면 마커 옆에 `(1차 확인 시도: 무엇을 봤고 왜 안 닫혔는지)`를 한 줄 남긴다 — 그래야 fact-checker가 같은 길을 다시 걷지 않는다.
  - **실측**: 초안이 안전측으로 격리한 항목을 검증자가 되레 확정 사실로 승격시킨 일이 다섯 편에서 났다(turbovec `ICLR 2026`·boris `82%`·claude5 `/doctor`·에이전트-팀·dogwood InfoQ). 그 다섯 번은 작가의 일을 검증자가 대신한 것이고, 그만큼이 검증 시간과 수정 루프로 돌아왔다. **근거 없는 확장이 오류이듯 근거 없는 유보도 오류다.**
  - 반대 방향의 실측도 있다 — 초안이 검증 전에 스스로 1차까지 내려간 편(에이전트-메모리-서베이)이 해석 FAIL 0으로 가장 깨끗했다.
- 반론을 선제 처리한다: "~라고 생각할 수 있다. 하지만 ...".

## 4. OKF v0.2 + knowledge-wiki 발행 프로필

OKF v0.2에서 항상 필수인 키는 `type` 하나다. 다만 이 위키는 검색·리뷰 품질을 위해 `title`, `description`, `tags`까지 필수로 요구한다. 이것은 OKF 자체의 필수 조건이 아니라 **knowledge-wiki 발행 프로필**이다.

```yaml
---
title: 표시 제목
type: 개념 | 도구 | 설계결정 | 레퍼런스 | 플레이북 # 자유값
description: 한 줄 요약 (index·검색·RAG에 쓰임)
tags: [소문자, 2~4개]
resource: https://…   # 특정 도구/레포/API를 다룰 때만
status: draft | stable | deprecated # 선택, 생략하면 stable
generated: { by: human:<id> | <producer>/<version>, at: <ISO 8601> } # 선택
verified: { by: human:<id> | process:<id> | <producer>/<version>, at: <ISO 8601> } # 실제 확인했을 때만
stale_after: YYYY-MM-DD # 시간 민감 노트만
sources:
  - id: source-key
    resource: https://…
    title: 원문 제목
---
```

- 내부 연결은 본문 문맥 속 `[[위키링크]]`를 쓴다. 이 위키는 Quartz로 렌더되고 기존 노트 전부가 이 형식이다. 없는 노트 링크도 stub로 허용한다.
- 외부 근거는 `sources`에 두고, 주장 뒤에 `[^source-key]`를 붙인 뒤 같은 라벨의 각주를 정의한다. 각주 라벨은 `sources[].id`와 일치해야 한다. 기존 `## 출처` 목록은 v0.1 호환 입력으로만 허용한다.
- `generated`는 현재 내용의 생성 주체와 마지막 의미 있는 변경 시점이다. `verified`는 출처나 `resource`에 실제 대조한 이벤트만 기록한다. 둘을 같은 뜻으로 쓰지 않는다.
- `status` 생략은 `stable`이다. `stale_after` 당일부터 오래된 것으로 판단한다.
- `index.md`와 `log.md`는 예약 파일이며 일반 개념 노트명으로 사용하지 않는다. 번들 루트 `index.md`에는 `okf_version: "0.2"`를 선언할 수 있다.
- `type: Attested Computation`이면 `runtime`이 필수다. `parameters`, `computation`, `executor`, `attester` 계약은 OKF v0.2 명세를 따른다.
- 파일명: kebab-case + `.md`. 한 파일 = 한 주제.
- AI 엔지니어링 주제는 `content/ai-엔지니어링/` 폴더에, 그 외는 `content/` 루트에.

## 5. 자기 점검 (제출 전)

- [ ] `00_domain_brief.md`에 도메인·용어 기준 출처 2개 이상·핵심 용어 표가 있는가
- [ ] 핵심 용어가 공식/대표 출처의 의미와 표기를 따르며 자의적 조어가 없는가
- [ ] 문체가 정확하고 절제됐으며 홍보성 수사·가벼운 구어체·근거 없는 자신감이 없는가
- [ ] 대상 독자 한 줄이 메타 주석에 있는가
- [ ] 결론이 서두에 있는가
- [ ] 모든 주장에 근거 또는 `(검증 필요)` 마커가 있는가
- [ ] 남긴 마커마다 1차 확인을 **시도**했고 그 결과가 한 줄 적혀 있는가 — 안 열어보고 단 마커는 없는가
- [ ] 두 사실을 잇는 문장(인과·비교·일반화)마다 그 **연결**의 근거가 있는가 — 양 끝 수치의 근거 말고. 표에 척도가 다른 값을 한 열에 세우지 않았는가
- [ ] 직접 센 수치마다 집계 명령·범위가 붙어 있는가 — 몇 주 뒤 남이 같은 값을 다시 낼 수 있는가
- [ ] 트레이드오프 섹션이 있는가
- [ ] 요약·리드·결론·표가 본문보다 강해지지 않았는가 — 본문의 유보 라벨과 원문의 한정어가 살아 있는가
- [ ] `type`과 위키 프로필의 `title`·`description`·`tags`가 있는가
- [ ] 외부 주장에 `sources` + 일치하는 각주가 있는가
- [ ] `generated`와 `verified`를 실제 의미대로 썼는가
- [ ] 관련 위키 노트 1개 이상 [[링크]]했는가
